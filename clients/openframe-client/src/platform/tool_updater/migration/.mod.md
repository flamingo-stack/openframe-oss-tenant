Defines the migration framework for transitioning installed tools between different installation types (e.g., Standard → GuiApp).

## Key Components

**`MigrationContext`** — Shared state carried through the migration lifecycle, tracking whether the old installation was cleaned up (`old_cleaned`) and whether the tool needs to be restarted post-migration (`needs_start`).

**`ToolMigrator` trait** — Async trait defining the four-phase migration contract:
- `prepare` — Pre-migration checks and context setup
- `migrate` — Performs the actual installation type transition
- `finalize` — Post-migration cleanup/activation
- `rollback` — Best-effort recovery on failure (default no-op with a warning log)

**`create_migrator()`** — Factory function that inspects the current `Installation` and target `InstallationType`, returning the appropriate `Arc<dyn ToolMigrator>` or `None` if no migration is needed. Currently supports `Standard → GuiApp` on macOS/Windows only; all other paths bail with an error.

**`needs_migration()`** — Lightweight check comparing the current installation type against the target, used to gate migration logic upstream.

## Usage Example

```rust
// Check if migration is needed before proceeding
if needs_migration(&current_installation, target_type) {
    let migrator = create_migrator(&current_installation, target_type, deps)?
        .expect("migration path must be supported");

    let ctx = migrator.prepare(&installed_tool).await?;

    let new_installation = migrator
        .migrate(&installed_tool, &download_config, &ctx)
        .await
        .inspect_err(|_| {
            // fire-and-forget rollback
        })?;

    migrator.finalize(&installed_tool, &new_installation, &ctx).await?;
}
```

> **Platform note:** `StandardToGuiAppMigrator` is only compiled on `macos` and `windows` targets. Adding new migration paths requires implementing `ToolMigrator` and registering the match arm in `create_migrator`.
