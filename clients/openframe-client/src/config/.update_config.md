Configuration constants for the update system, defining timeouts, retry policies, and messaging parameters used across download, HTTP client, consumer, and reconnection subsystems.

## Key Components

| Constant | Value | Purpose |
|---|---|---|
| `MAX_DOWNLOAD_RETRIES` | `3` | Maximum attempts per download |
| `DOWNLOAD_TIMEOUT_SECS` | `300s` | Binary download timeout |
| `MIN_BINARY_SIZE_BYTES` | `100 KB` | Minimum valid binary size guard |
| `HTTP_CLIENT_TIMEOUT_SECS` | `120s` | Control-plane requests (auth, registration, heartbeat) |
| `DOWNLOAD_CLIENT_TIMEOUT_SECS` | `300s` | Binary downloads (GitHub, Artifactory, tool API) |
| `CONSUMER_RETRY_ATTEMPTS_PER_CYCLE` | `5` | Retries before pausing a cycle |
| `INITIAL_RETRY_DELAY_MS` | `1000ms` | Starting backoff delay |
| `MAX_RETRY_DELAY_MS` | `30000ms` | Backoff ceiling |
| `CONSUMER_CYCLE_PAUSE_MS` | `30000ms` | Pause between retry cycles |
| `RECONNECTION_DELAY_MS` | `5000ms` | Delay before reconnect attempt |
| `CONSUMER_ACK_WAIT_SECS` | `120s` | NATS consumer ack deadline |
| `CONSUMER_MAX_DELIVER` | `10` | NATS max delivery attempts |

## Usage Example

```rust
use crate::update_config::{
    MAX_DOWNLOAD_RETRIES,
    DOWNLOAD_TIMEOUT_SECS,
    INITIAL_RETRY_DELAY_MS,
    MAX_RETRY_DELAY_MS,
};

// Exponential backoff using config constants
let mut delay = INITIAL_RETRY_DELAY_MS;
for attempt in 0..MAX_DOWNLOAD_RETRIES {
    match download_binary(url, DOWNLOAD_TIMEOUT_SECS).await {
        Ok(bytes) => break,
        Err(_) => {
            tokio::time::sleep(Duration::from_millis(delay)).await;
            delay = (delay * 2).min(MAX_RETRY_DELAY_MS);
        }
    }
}
```

> Adjust these constants to tune aggressiveness of retries and timeouts without touching business logic — all subsystems reference this single source of truth.
