Manages the lifecycle of tool connection processing for installed MSP tools, handling agent ID resolution, connection publishing, and retry logic with concurrency safety.

## Key Components

**`ToolConnectionProcessingManager`** — Central struct coordinating tool connection workflows via:
- `installed_tools_service` — Retrieves all installed tools
- `params_processor` — Resolves command argument placeholders
- `tool_connection_publisher` — Publishes connection messages to the broker
- `config_service` — Provides machine identity
- `tool_connection_service` — Persists connection records
- `running_tools: Arc<RwLock<HashSet<String>>>` — Tracks in-flight connections to prevent duplicate processing

**Key Methods:**

| Method | Description |
|--------|-------------|
| `run()` | Processes all installed tools on startup, skipping existing connections |
| `run_new_tool()` | Handles a single newly installed tool |
| `try_mark_running()` | Atomically claims a tool slot; returns `false` if already running |
| `clear_running_tool()` | Releases a tool's slot after processing completes |
| `process_tool()` | Spawns an async retry loop: resolves agent ID via subprocess, publishes connection, persists record |

## Usage Example

```rust
let manager = ToolConnectionProcessingManager::new(
    installed_tools_service,
    params_processor,
    tool_connection_publisher,
    config_service,
    tool_connection_service,
);

// On agent startup — process all installed tools
manager.run().await?;

// When a new tool is installed at runtime
manager.run_new_tool(installed_tool).await?;

// Release slot if external cancellation occurs
manager.clear_running_tool(&tool_id).await;
```

> **Retry behavior:** All failure paths (command error, timeout, empty output, publish failure) retry after `RETRY_DELAY_SECONDS` (15s). The loop breaks only on successful publish + save.
