Manages the lifecycle of tool processes across platforms, handling process launching, session detection, and retry logic for installed tools in the Flamingo/OpenFrame agent runtime.

## Key Components

- **`get_active_user_session()`** *(Windows-only)* — Detects the active Windows Terminal Services session, preferring RDP sessions over console, used to determine where to spawn processes
- **`launch_process_in_console_session()`** *(Windows-only)* — Spawns a process in the physical console session using `WTSGetActiveConsoleSessionId` + `CreateProcessAsUserW`
- **`launch_process_in_user_session()`** *(Windows-only, pub)* — Public entry point that resolves the best active session then delegates to `launch_process_in_target_session`
- **`launch_process_in_target_session()`** *(Windows-only, pub)* — Core Windows process launcher: acquires + duplicates a user token, builds the command line, and calls `CreateProcessAsUserW` with `winsta0\default` desktop targeting; includes a fallback retry without desktop specification
- **`RETRY_DELAY_SECONDS`** — Constant (5s) controlling retry backoff for failed tool launches

### Dependencies
- `InstalledToolsService`, `ToolCommandParamsResolver`, `ToolKillService` — service layer for tool lifecycle management
- `WindowsSessionManager` / `windows_helpers` — Windows-specific session and command-line utilities
- `tokio` async runtime with `RwLock`, `AtomicBool` for concurrent state management

## Usage Example

```rust
#[cfg(target_os = "windows")]
use crate::services::tool_run_manager::launch_process_in_user_session;

// Launch a tool in the active user's desktop session
let exe_path = "C:\\Program Files\\MyTool\\tool.exe";
let args = vec!["--config".to_string(), "default".to_string()];

match launch_process_in_user_session(exe_path, &args) {
    Ok((pid, handle)) => {
        info!("Tool launched with PID: {}", pid);
        // Store handle for later termination via ToolKillService
    }
    Err(e) => {
        error!("Failed to launch tool: {}", e);
        // Retry after RETRY_DELAY_SECONDS
    }
}
```

> **Note:** On Windows, this module requires elevated privileges to call `WTSQueryUserToken` and `CreateProcessAsUserW`. The session detection logic prioritizes active RDP sessions over console sessions when multiple sessions are present.
