Orchestrates MeshCentral remote file management operations by coordinating tunnel connections, file transfers, directory listings, and search functionality through a unified API.

## Key Components

| Export | Description |
|--------|-------------|
| `MeshCentralFileManager` | Main class managing file operations over an encrypted MeshCentral tunnel |

**Private subsystems:**

| Component | Role |
|-----------|------|
| `MeshTunnel` | WebSocket tunnel (protocol 5) to the remote node |
| `FileOperations` | Low-level file CRUD primitives |
| `FileUploader` | Chunked upload with hash deduplication |
| `FileDownloader` | Streaming binary download with progress |
| `FileBinaryProtocol` | Binary frame encode/decode |
| `FileErrorHandler` | Centralised error normalisation |

**State machine** (`FileConnectionState`): `disconnected` → `connecting` → `connected_to_server` → `connected_end_to_end`

## Usage Example

```typescript
import { MeshCentralFileManager } from './file-manager';

const manager = new MeshCentralFileManager({
  isRemote: true,
  nodeId: 'node123abc',
  controlClient: meshControlClientInstance,
  onStateChange: state => console.log('State:', state),
  onTransferProgress: (progress: FileTransferProgress) => {
    console.log(`${progress.fileName}: ${progress.percent}%`);
  },
  onError: err => console.error('File manager error:', err),
  onServerCancelDownload: (fileName, reason) =>
    console.warn(`Download cancelled — ${fileName}: ${reason}`),
});

// Establish tunnel (fetches auth cookies automatically)
await manager.connect();

// Directory listing and transfers are triggered internally
// via JSON/binary messages dispatched through the tunnel callbacks.
```

## Notes

- `connect()` only supports **remote** mode; local server access throws.
- Path normalisation (`normalizeRequestedPath`) transparently converts Unix-style paths (e.g. `/C:/Users`) to Windows UNC format (`C:\Users`).
- Search requests are debounced; stale results from cancelled `reqid`s are discarded via `cancelledSearchRequestIds`.
- All inbound tunnel frames are routed by `handleJsonMessage` / `handleBinaryMessage`, with binary frames falling back to JSON detection before being forwarded to the active downloader.
