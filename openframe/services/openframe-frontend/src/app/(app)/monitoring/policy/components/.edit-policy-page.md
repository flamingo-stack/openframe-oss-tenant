A page component for creating and editing monitoring policies, including policy name/description, an SQL query editor, device assignment, and a live test panel.

## Key Components

- **`EditPolicyPage`** — Main exported component accepting a `policyId` prop (`null` for new policies, string ID for edits)
- **`policyFormSchema`** — Zod validation schema enforcing a required `name`, optional `description`, and `query` fields
- **`getDeviceKey`** — Helper that extracts a Fleet host ID string from a `Device` object for the device selector

## Key Hooks Used

| Hook | Purpose |
|------|---------|
| `usePolicyDetails` | Fetches existing policy data |
| `usePolicies` | Provides `createPolicy` / `updatePolicy` mutations |
| `usePolicyHosts` / `useReplacePolicyHosts` | Manages device host assignments |
| `usePolicyDevices` | Loads available devices for selection |
| `useLiveCampaign` | Manages live query test execution state |

## Usage Example

```typescript
// In a Next.js page (e.g. /monitoring/policy/[id]/edit)
import { EditPolicyPage } from './edit-policy-page';

export default function Page({ params }: { params: { id: string } }) {
  return <EditPolicyPage policyId={params.id} />;
}

// For creating a new policy
export default function NewPolicyPage() {
  return <EditPolicyPage policyId={null} />;
}
```

## Behaviour Notes

- In **edit mode**, existing policy data and host assignments are pre-populated via `reset()` on load
- **Save** is disabled until a name is entered; **Test Policy** is disabled until a query is written
- On save, host assignments are applied via `replacePolicyHostsMutation` after the policy upsert; host-sync failures are handled silently (toast shown by the mutation hook)
- The `LiveTestPanel` runs an ad-hoc osquery campaign against selected devices and can be re-triggered without closing
